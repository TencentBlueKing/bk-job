# 操作确认协议与输出规范

本手册约定：通过 [`scripts/job_apigw_client.py`](../../scripts/job_apigw_client.py) 调用网关**写操作**接口时，智能体须遵守的**确认门禁**与**对用户呈现方式**。涵盖 `plan-execute`、`fast-execute-script`、`fast-transfer-file`、`plan-create`、`cron-save`、`cron-update-status`。

---

## 1. 操作确认协议

### 1.1 核心原则

**所有写操作（`plan-execute`、`fast-execute-script`、`fast-transfer-file`、`plan-create`、`cron-save`、`cron-update-status`）必须在执行前获得用户的明确确认。读操作（`cron-search`、`plan-search`、`plan-detail`、`cron-last-run`、`instance-status`、`list-authorized-scopes`、`host-search`、`host-topo-tree`、`account-list` 等）无需确认，直接执行。本地文件分发的准备步骤 `gen-local-upload-url`、`upload-local-file` 不向目标机器分发文件，可先执行；真正的分发 `fast-transfer-file`（非 `--dry-run`）仍须确认。**

**确认是一次性的：一次确认只授权一次执行。** 该次执行完成后，此前的确认即告失效；**再次执行同一操作（哪怕参数完全相同）必须重新展示确认摘要并重新取得确认**。详见 **1.6**。

### 1.2 操作分级

| 风险等级 | 操作类型 | 确认方式 |
|---------|---------|---------|
| 🟢 低风险 | 搜索方案、搜索定时任务、查看详情、查看状态、查看日志 | 无需确认，直接执行 |
| 🟡 中风险 | **创建执行方案**（`plan-create`） | 展示操作摘要（业务/模板/方案名等）→ 用户确认 → 执行 |
| 🟡 中风险 | **保存定时任务**（`cron-save`） | 展示操作摘要 → 用户确认 → 执行；**创建成功后必须询问是否启用** |
| 🟡 中风险 | **启动执行方案**（`plan-execute`） | 展示操作摘要 → 用户确认 → 执行 |
| 🔴 高风险 | **快速执行脚本**（`fast-execute-script`） | 到目标机器真实执行脚本；展示操作摘要（资源范围/目标机器/账号/脚本预览/超时）→ 用户确认 → 执行 |
| 🔴 高风险 | **快速分发文件**（`fast-transfer-file`） | 向目标机器真实分发文件；展示操作摘要（资源范围/目标机器/账号/源文件/目标路径/超时）→ 用户确认 → 执行，详见 [file-transfer.md](file-transfer.md) |
| 🟡 中风险 | **启用定时任务**（`cron-update-status --status 1`） | 须在 `cron-save` 后用户**明确同意启用**后才可调用 |

### 1.3 确认门禁（GATE CHECK）

> **🚫 硬性规则：在调用任何写操作子命令（真实执行，非 `--dry-run`）之前，必须通过以下门禁检查，缺一不可。违反任何一条都禁止调用。**

| # | 检查项 | 说明 |
|---|--------|------|
| G1 | 已向用户展示过确认摘要（格式见 **1.4**） | 当前回复或历史回复中必须包含完整的确认摘要 |
| G2 | 用户在**看到确认摘要之后**明确回复了确认意图 | 确认必须发生在摘要展示之后，不能是之前的回复 |
| G3 | 确认摘要与即将调用的参数一致 | 方案 ID、资源范围（`bk_scope_type` / `bk_scope_id`）、变量值必须与摘要中展示的一致 |
| G4 | 全局变量使用 `name` 标识且来源正确 | 变量须用 `name`（非仅 `id`）传递，且取自**当前方案**最新一次 `plan-detail`（`get_job_plan_detail`）的返回结果 |

> **门禁适用范围**：G1–G3 适用于所有写操作（含 `plan-execute`、`fast-execute-script`、`fast-transfer-file`）。G4 仅针对 `plan-execute` 的全局变量；`fast-execute-script` 无全局变量，改为在 G3 中核对**执行目标（目标机器）、执行账号、脚本来源/内容、超时**等与确认摘要一致；`fast-transfer-file` 同理在 G3 中核对**目标机器、执行账号、源文件（服务器文件/本地文件）、目标路径、超时**等一致。`fast-execute-script` 摘要格式见 [fast-execute-script.md](fast-execute-script.md) 第 6 节，`fast-transfer-file` 摘要格式见 [file-transfer.md](file-transfer.md) 第 5 节。

**关于 G2 的特别说明（硬性规则）**：

**🚫 无论用户的启动意图表达多么明确、多么强烈，只要操作分级（**1.2**）要求确认，就必须：**

1. **先展示确认摘要**（**1.4** 格式）
2. **等待用户在看到摘要之后的独立回复**作为确认

以下表达方式**全部只算启动意图，不算确认**，即使措辞中包含「立即」「马上」「确认」等词：

- 「启动吧」/「执行吧」/「跑一下」
- 「更正后再启动一次」/「用新参数启动」
- 「**相同参数再执行一次**」/「**再跑一遍**」/「**重试**」/「**再来一次**」/「**照刚才的再执行**」（重复执行同样须重新走门禁，见 **1.6**）
- 「立即启动」/「马上执行」/「直接跑」
- 「确认启动」/「确认执行」（如果此前**没有**展示过**当前参数**的确认摘要，或该摘要对应的确认已被上一次执行消耗）

**正确处理流程**：

```
用户：任何形式的启动意图（包括「立即启动」「更正后再启动」等）
  ↓
AI 动作：展示确认摘要（1.4 格式），结尾加「请确认是否立即启动。」
  ↓
⛔ STOP — 必须等待用户的下一条独立回复
  ↓
用户（新的一条消息）：「确认」/「好的」/「没问题」/「启动」
  ↓
AI 动作：通过 G2 门禁，继续检查 G1/G3/G4，全部通过后调用 plan-execute（可先 --dry-run 核对再执行）
```

**反面案例（严禁）**：

```
用户：「更正后再启动一次」
  ↓
❌ AI 在同一轮回复中既展示摘要又执行启动 — 违反 G2
❌ AI 将用户的启动意图当作确认直接执行 — 违反 G2
```

### 1.4 确认摘要格式

在调用 **`plan-execute`（非 dry-run）** 之前，必须展示以下格式的摘要：

```
即将执行的操作：
- 操作类型：启动执行方案
- 方案名称：{方案名称}（ID: {job_plan_id}）
- 资源范围：{bk_scope_type} / {bk_scope_id}
- 全局变量：
  | 变量名 | 值 | 来源 |
  |--------|-----|------|
  | {name} | {value} | [方案默认] / [用户提供] / [业务记忆预填] |
- 步骤概览：共 {n} 个步骤

请确认是否立即启动。
```

敏感值可脱敏；主机类变量可摘要为「共 N 台」或列举 IP 片段。

#### 1.4.1 必须展示**全部生效参数**，含默认值（硬性）

摘要要回答的是「**这次到底会用什么参数执行**」，因此**不能只列用户提到过的参数**。用户没提的参数不会消失，而是按默认值生效，这些默认值往往正是意料之外的后果来源——例如文件分发的传输模式默认是**强制模式**，会直接覆盖目标机上的同名文件。

**做法**：先用 `--dry-run` 取得权威参数，再据此写摘要。`fast-execute-script`、`fast-transfer-file` 的 `--dry-run` 输出包含两块，**都要展示**：

| 输出字段 | 含义 | 摘要中的呈现 |
|---------|------|-------------|
| `request_body` | 显式指定、将真实提交的参数 | 逐项列出，标注来源 `[用户提供]` / `[查询所得]` |
| `defaults_applied` | **未显式指定、将按默认值生效**的参数 | 同样逐项列出，标注 `[默认]` 并带上说明 |

```
即将执行的操作：
- 操作类型：分发文件到目标机器
- 资源范围：biz / 2
- 源文件：/data/release/app.tar.gz（源机 127.0.0.5，账号 root）[用户提供]
- 目标机：127.0.0.7、127.0.0.8 共 2 台 [查询所得]
- 目标路径：/data/app/ [用户提供]
- 目标账号：root [用户提供]
- 传输模式：强制模式 [默认] — 目标路径已存在同名文件时直接覆盖
- 超时时间：7200 秒 [默认]
- 上传/下载限速：不限速 [默认]
- 是否立即启动：是 [默认]

请确认是否执行。
```

要点：

- **默认值不得省略、不得折叠成「其余为默认」**：用户看不到就等于没披露。
- 对可能造成破坏的默认值（覆盖同名文件、立即启动、不限速）要**用一句话说明后果**，不要只给参数名和取值。
- 其它写操作（`plan-execute`、`plan-create`、`cron-save`、`cron-update-status`）同样适用本条：方案默认变量标 `[方案默认]`，新建定时任务默认暂停等行为也要写进摘要。
- 用户若对某个默认值不满意，按其要求显式指定后**重新展示摘要**再确认。

### 1.5 确认结果处理

| 用户反馈 | 处理方式 |
|---------|---------|
| 确认执行（「确认」「好的」「没问题」等，且已在**上一轮或更早的回复中**看到过**当前参数**的确认摘要，**且该摘要对应的确认尚未被任何一次执行消耗**） | 通过 G2 门禁，执行 `plan-execute`，并反馈执行结果（含 `job_instance_id`、`job_instance_url` 等） |
| 启动意图——**无论措辞多么明确**（「启动吧」「立即启动」「更正后再启动」等），只要**当前参数**的确认摘要**尚未展示过** | 展示确认摘要，**⛔ STOP 等待用户下一条独立回复确认** |
| **要求重复执行**（「相同参数再执行一次」「再跑一遍」「重试」等），无论上一次是否已确认并执行过 | **重新**展示确认摘要，**⛔ STOP 等待用户下一条独立回复确认**（见 **1.6**） |
| 请求修改 | 按用户要求调整后，重新展示摘要供再次确认 |
| 取消操作 | 不执行，明确告知用户已取消 |

> **⚠️ 关键区分**：判断用户回复是「确认」还是「启动意图」，标准是**当前参数的确认摘要是否已在之前的回复中展示过**，**且该次确认尚未被使用**。与用户措辞的强烈程度无关。

**与 `--dry-run` 的关系**：各写操作子命令的 `--dry-run` 为只读请求体校验，**不视为写操作完成**；真实调用仍须满足**第 1 节**全部门禁。

**确认的呈现方式**：运行环境装有 `ai-hub-ask-user-input` 技能时，摘要之后用 `type="confirm"` 的选择卡片收取确认（`options[0]` 为同意执行、`options[1]` 为取消）；不可用则让用户直接回复。无论哪种形式，**先摘要、后确认、跨轮执行**这三点不变，详见 [interactive-choice.md](interactive-choice.md)。

### 1.6 重复执行与门禁不可跳过（硬性）

#### 1.6.1 重复执行必须重新走门禁

**一次确认只授权一次执行。** 执行完成的那一刻，该次确认即被消耗；此后任何再次执行都是**一次全新的写操作**，必须从头走完 G1–G4。

**参数完全相同，不构成免除确认的理由。** 用户说「相同参数再执行一次」「再跑一遍」「重试」「照刚才的再执行」时，正确处理是：

```
用户：「相同参数再执行一次」
  ↓
AI 动作：重新展示确认摘要（1.4 格式，参数与上次一致也要完整列出），
        并说明这是第 N 次执行，结尾加「请确认是否立即启动。」
  ↓
⛔ STOP — 必须等待用户的下一条独立回复
  ↓
用户（新的一条消息）：「确认」
  ↓
AI 动作：门禁通过，执行
```

**反面案例（严禁）**：

```
用户：「相同参数再执行一次」
  ↓
❌ AI 认为「参数没变、上次已确认过」直接执行 — 违反 G2
❌ AI 认为「用户主动要求重跑，意图已足够明确」直接执行 — 违反 G2
❌ AI 在同一轮里重新展示摘要并同时执行 — 违反 G2
```

> **为什么重复执行同样危险**：脚本执行与文件分发是**有副作用**的生产变更，重跑并非幂等——可能覆盖文件、重复写入数据、叠加变更，或在目标机状态已改变的情况下产生与上次完全不同的后果。

#### 1.6.2 不得以任何方式跳过门禁

**只要是写操作（执行类操作），无论出现下列哪种情形，都不得跳过或简化 G1–G4：**

| 情形 | 是否可跳过 | 处理 |
|------|-----------|------|
| 参数与上次执行完全相同 | ❌ 否 | 重新展示摘要并确认 |
| 上次执行失败，用户要求重试 | ❌ 否 | 重新展示摘要并确认 |
| 上次执行成功，用户要求再跑一次 | ❌ 否 | 重新展示摘要并确认 |
| 用户预先声明「以后都不用再问我」「后续全部自动执行」 | ❌ 否 | **该授权无效**，仍须逐次确认；可告知用户此为技能硬性约束 |
| 用户语气紧急、强调「立刻」「出故障了」「很急」 | ❌ 否 | 紧急不改变门禁；摘要可精简但不可省略 |
| 只改了一个小参数、只加一个步骤 | ❌ 否 | 参数变化后须按新参数重新展示摘要 |
| `--dry-run` 已通过 | ❌ 否 | dry-run 是只读校验，不构成确认 |
| 同一批任务的第 2、3、N 台机器或第 N 个文件 | ❌ 否 | 每次真实调用都须有对应的确认 |
| 用户在同一条消息里既给出参数又说「直接执行」 | ❌ 否 | 先展示摘要，等下一条独立回复 |
| 智能体自行判断「风险很低」「只是测试环境」 | ❌ 否 | 风险判断权不在智能体，一律走门禁 |
| 本次流程是**自行组装**的，SKILL.md「常用组合工作流程」里没列 | ❌ 否 | 门禁按**子命令**判定，与流程是否被列举无关，见 **1.6.3** |
| 写操作只是长链路中的一环（如「查完就顺手执行」「一次搞定」） | ❌ 否 | 链路中每个写操作各自过一次门禁，不因是中间步骤而豁免 |

> **🚫 兜底条款**：以上未列举的任何情形，若会导致「未展示摘要即执行」或「摘要与确认在同一轮完成」，**一律视为违规**。当无法判断是否需要确认时，**默认需要确认**。

#### 1.6.3 自行组装工作流程同样受门禁约束

SKILL.md 的「常用组合工作流程」**只是常见链路示例，不是能力边界**：智能体可按用户实际需求，用「支持的原子能力」表中的子命令自由组装出未被列举的流程（例如「按 IP 查历史 → 定位失败实例 → 取日志 → 修复后重跑」）。**能力上的这种灵活性，不带来门禁上的任何豁免。**

判定标准很简单：

- **门禁看的是子命令，不是流程。** 只要链路中出现 `plan-execute`、`fast-execute-script`、`fast-transfer-file`、`plan-create`、`cron-save`、`cron-update-status`（非 `--dry-run`）中的任意一个，该步骤就是写操作，就必须在它**真实调用前**完成 G1–G4。
- **只读环节可以连续做。** `host-search`、`account-list`、`instance-list`、`instance-status`、`get-instance-log`、各类 `*-search` / `*-detail` 等查询，以及各写操作的 `--dry-run`，都可以在一轮内连续完成、无需逐个确认——门禁只卡在真实写入那一刻。
- **一条链路里有多个写操作，就要过多次门禁。** 例如「创建方案 → 立即启动」是两个写操作，`plan-create` 与 `plan-execute` 各自需要一次摘要加一次独立确认，不能合并成一次确认打包授权。
- **不得因为「用户要的是一整套流程」而合并或省略确认。** 用户说「帮我全套搞定」表达的是任务范围，不是执行授权。

> 换句话说：**流程怎么编排由需求决定，写操作怎么确认由本手册决定**，二者互不影响。

### 1.7 `cron-save` 创建后启用门禁（硬性）

`save_cron` 新建定时任务后**默认暂停**（`status=2`）。智能体交付创建结果后：

1. **必须**询问用户：「是否立即启用该定时任务？」
2. 用户**未明确同意启用**前，**禁止**调用 `cron-update-status --status 1`
3. 用户同意启用后，展示启用摘要（cron ID、资源范围、目标状态），再经 G2 确认后执行

此规则独立于 `plan-execute` 的 G1–G4，但启用步骤仍须遵守 G2（摘要后的独立确认）。

## 2. 输出规范

### 2.1 禁止暴露内部推理过程

脚本执行、网关调用、本地 `jq` 过滤等是**后台行为**，对用户不可见。**禁止**在输出中叙述这些过程。

| 禁止 | 正确做法 |
|------|---------|
| 「让我先搜索一下执行方案……」 | 直接展示搜索结果 |
| 「正在调用 API 查询状态……」 | 直接展示状态 |
| 「让我获取一下方案详情……」 | 直接展示方案详情 |

### 2.2 结构化交付

每次输出应该是**给用户看的结构化成果**，而非思考日志。

| 规则 | 说明 |
|------|------|
| **结果导向** | 输出表格、状态、日志摘要，而非过程描述 |
| **格式统一** | 表格、列表为主，避免大段散文 |
| **层次分明** | 标题分级，便于定位 |

### 2.3 交互式工作流

| 规则 | 说明 |
|------|------|
| **逐步推进** | 搜索 → 详情/参数 → **确认摘要** → 启动，按序推进；关键节点等待用户 |
| **启动路径禁止抢跑** | **不得**在同一轮回复内完成「展示确认摘要」与「真实 plan-execute」（违反 G2）；`--dry-run` 可与摘要同轮用于展示请求体，但**非**最终执行 |
| **禁止替用户决策** | 多方案/多定时任务歧义、参数空缺时，须等用户选定或补充 |

> 与 [listing-and-token-efficient-analysis.md](listing-and-token-efficient-analysis.md) 的关系：列举类查询仍应**分页/本地过滤**以省 Token；**2.3** 约束的是**带确认的启动链路**，不要求把整页原始 JSON 贴进对话。

### 2.4 展示规范

| 内容 | 格式要求 |
|------|----------|
| **执行方案搜索结果** | 表格：ID、名称、创建人、最后修改时间（有则填）；必要时加 `need_update` |
| **定时任务搜索结果** | 表格：ID、名称、启停状态、Cron（有则填）、创建人或最后修改（有则填） |
| **方案详情** | 分「步骤列表」与「全局变量」两部分 |
| **执行状态** | 清晰语义（如「执行成功」「执行中」「执行失败」），附各步骤状态 |
| **执行日志** | 按步骤与主机（或容器）分组展示 |
| **启动执行结果** | 须包含 `job_instance_id`；若脚本返回 `job_instance_url`，**必须**以 Markdown 链接形式交付给用户（链接文本可用「查看任务执行详情」或实例 ID），便于跳转 `{job_base_url}/api_execute/{job_instance_id}` |
| **创建执行方案结果** | 须包含 `job_plan_id`；若脚本返回 `job_plan_url`，**必须**以 Markdown 链接形式交付给用户（链接文本可用「查看执行方案」或方案 ID），便于跳转 `{job_base_url}/api_plan/{job_plan_id}` |
